| 方法   | 核心语义                  | 典型场景                          | 参数使用特点                                  | 幂等性       | 安全性（不修改资源） |
|--------|---------------------------|-----------------------------------|-----------------------------------------------|--------------|----------------------|
| **GET**  | 获取/查询资源             | 查看用户详情、列表分页查询        | 仅用路径参数（定位资源）和URL参数（筛选条件），无请求体 | 是（多次查询结果一致） | 是（仅读取，不修改） |
| **POST** | 创建资源/执行非标准操作   | 注册新用户、提交订单、支付操作    | 路径参数（可选，定位父资源）+ 请求体（核心数据）       | 否（多次调用可能结果不同） | 否（可能创建/修改资源） |
| **PUT**  | 全量更新已有资源（替换）  | 完整修改用户信息、覆盖订单详情    | 路径参数（必须，定位资源）+ 请求体（资源完整信息）     | 是（多次更新结果一致） | 否（修改资源）       |
| **DELETE** | 删除资源                 | 删除用户、取消订单                | 仅用路径参数（定位资源），无需请求体或URL参数         | 是（多次删除结果一致） | 否（删除资源）       |
| **PATCH** | 部分更新已有资源          | 修改用户昵称、调整商品部分属性    | 路径参数（定位资源）+ 请求体（仅需修改的字段）         | 是（多次部分更新结果一致） | 否（修改资源）       |


**关键原则**
- 语义优先：通过 “方法 + 路径” 即可直观判断接口用途（如GET /users是查列表，POST /users是创建用户）。
- 幂等性区分：
    - 幂等方法（GET/PUT/DELETE/PATCH）适合重试（如网络抖动时重发请求，结果不变）；
    - 非幂等方法（POST）需谨慎重试（如支付接口，多次调用可能重复扣款）。
- 参数配合：
    - 路径参数：定位资源（如/users/123中的123）；
    - URL 参数：筛选 / 分页（如?page=1）；
    - 请求体：传递复杂数据（创建 / 更新的内容）。

遵循这些规则，能让接口设计更规范、易理解，减少团队协作成本和潜在风险。

`纯技术实现角度,HTTP 协议本身并没有 “强制限制” 某种操作必须用特定方法（比如浏览器不会阻止你用GET删数据，服务器也能解析POST的查询参数,get请求也可以从url参数中获取参数来删除服务器数据），不存在 “技术壁垒”。`
但这里的关键是：技术上的 “可行” 不等于工程上的 “合理”。HTTP 方法的选择，本质是对 “语义约定” 的遵守，而这些约定背后是降低系统复杂度、规避风险的工程智慧。

以下是 HTTP 五种常用方法（GET、POST、PUT、DELETE、PATCH）的核心语义总结，聚焦 “操作意图” 和 “资源关系”：
| 方法      | 核心语义（一句话概括）                          | 关键特征                                  | 类比理解                  |
|-----------|-------------------------------------------------|-------------------------------------------|---------------------------|
| **GET**   | **获取已有资源**（只读，不修改服务器状态）      | - 仅查询，不产生副作用<br>- 可被缓存<br>- 参数在URL中传递 | 像“查阅档案”，只看不动    |
| **POST**  | **创建新资源**或**执行非标准操作**              | - 会产生新资源或状态变化<br>- 非幂等（多次调用可能结果不同）<br>- 数据在请求体中传递 | 像“提交申请表”，可能生成新档案 |
| **PUT**   | **全量更新已有资源**（用新数据完全替换旧资源）  | - 操作对象是“已存在的特定资源”<br>- 幂等（多次调用结果一致）<br>- 请求体包含资源完整信息 | 像“替换整个档案”，旧内容全覆盖 |
| **DELETE**| **删除已有资源**                                | - 移除指定资源<br>- 幂等（多次调用结果一致）<br>- 通常仅需通过路径定位资源 | 像“销毁档案”，删后再删结果相同 |
| **PATCH** | **部分更新已有资源**（仅修改资源的部分字段）    | - 操作对象是“已存在的特定资源”<br>- 幂等（多次调用结果一致）<br>- 请求体仅包含需修改的字段 | 像“修改档案中的某几页”，其他内容不变 |

**核心原则：方法语义应与 “操作对资源的影响” 严格匹配。看到方法名，就能直观判断是 “查、创、全量改、部分改、删”，这是 HTTP 设计的核心价值。**
